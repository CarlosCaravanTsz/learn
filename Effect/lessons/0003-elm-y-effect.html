Conectar Effect con el ciclo de Elm

El Model guarda el estado. Un Message describe qué pasó. update calcula el próximo Model y view deriva la pantalla de ese estado.

Un clic cambia el estado

Model Idle + Message Load("42") → update → Model Loading

update se parece al reducer de useReducer. Para los mismos argumentos devuelve la misma transición y no modifica el Model recibido. view(Loading) muestra «Cargando…». La unión discriminada de Model le permite a TypeScript comprobar que solo Ready contiene un perfil. The Elm Architecture · React useReducer

El clic también puede pedir trabajo

Model Idle + Message Load("42") → update → Model Loading
                                        → Command { id, request }

En el ejemplo, el Command es un objeto que describe una carga. update devuelve el objeto y el runtime lo interpreta fuera de la transición. En Foldkit, los Commands ejecutan Effects que producen mensajes de resultado. React useEffect tiene otra responsabilidad: sincronizar un componente con un sistema externo después de que React actualiza la pantalla. Arquitectura de Foldkit · React Synchronizing with Effects

El resultado vuelve por el mismo camino

Model Idle + Message Load("42") → update → Model Loading
                                        → Command → Effect → Message Loaded
Model Loading + Message Loaded  → update → Model Ready → view

Effect.match convierte un éxito en Loaded y un fallo esperado en LoadFailed. Los dos regresan a update. El número request empareja la respuesta con la carga activa. Si pediste A y luego B, la respuesta de A queda descartada aunque llegue mientras B carga. Una subscription aporta mensajes desde una fuente continua, como el teclado o un reloj, mientras la aplicación necesita escucharlos. HTTP en Elm · Arquitectura de Foldkit

Práctica

Abre 03-elm-loop.ts y corre npm run elm. El ejemplo entrega deliberadamente el fallo antiguo mientras la segunda carga está activa. Retira || model.request !== message.request de la condición en update y vuelve a correrlo. Después restaura la condición e intercambia el orden de entrega de las dos respuestas. Ajusta las aserciones para comprobar que «Ada» permanece visible.

Comprobar el resultado

Sin comprobar el número de petición, el fallo antiguo muestra Error: RequestError donde la aserción esperaba «Cargando…». Con la condición restaurada y la respuesta nueva primero, el modelo pasa a Ready. La respuesta vieja que llega después deja el modelo en Ready, así que las dos aserciones deben esperar «Ada».

Si quieres revisar una transición concreta, trae el Model anterior y el Message. Podemos calcular la salida de update sin ejecutar la carga.
