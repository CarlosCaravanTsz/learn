Lección 0001 · Foldkit

El loop: cómo piensa una aplicación Foldkit

La única idea que tienes que interiorizar hoy: en Foldkit, todo lo que ocurre es un Message, y un único lugar decide qué significa. Quince minutos de lectura y un quiz.

Material de apoyo: Glosario de Foldkit · Mapa React → Foldkit

Por qué esto, para ti

Tu objetivo es construir el frontend de un backend Effect. Foldkit existe exactamente para eso: lleva los patrones de Effect (Schema, servicios, Effects como valores) al navegador, montados sobre The Elm Architecture (foldkit.dev). Vienes de React: no vas a aprender "otro framework de componentes", vas a aprender una forma distinta de organizar estado y efectos donde nada queda enterrado en handlers.

El ciclo

Toda app Foldkit repite el mismo ciclo, siempre (doc: Architecture):

Algo sucede
(clic, HTTP, timer) → Message → update
(pura) → Model + Commands → view (pura) → HTML
Navegador

El runtime ejecuta los Commands y su resultado vuelve como otro Message: el ciclo se cierra en update, siempre.

Los Messages nacen de cinco fuentes: el navegador (clics, teclado), los Commands (resultados de efectos), los Mounts (trabajo atado a un elemento DOM), las Subscriptions (streams activos mientras el Model lo pida) y los ManagedResources (handles con estado). Ninguna de ellas toca el Model: reportan hechos, y solo update decide el siguiente estado.

Los cuatro artefactos, en código real

El counter canónico de la documentación (Coming from React), completo:

// MODEL — el estado de TODA la aplicación, definido con Schema de Effect
const Model = Schema.Struct({
  count: Schema.Number,
})
type Model = typeof Model.Type

// MESSAGE — la unión de hechos que pueden ocurrir
const Message = defineMessageUnion({
  ClickedIncrement: {},
})
type Message = typeof Message.Type

// UPDATE — función pura: (Model actual, Message) → { model, commands? }
const update = (model: Model, message: Message) =>
  Message.match<Update.Return<Model, Message>>(message, {
    ClickedIncrement: () => ({
      model: modifyFields(model, { count: count => count + 1 }),
    }),
  })

// VIEW — función pura del Model a HTML; los handlers CONSTRUYEN Messages
const view = (model: Model, h: HtmlBuilder<Message>): Document => ({
  title: `Count: ${model.count}`,
  body: h.div([], [
    h.p([], [`Count: ${model.count}`]),
    h.button([h.OnClick(Message.ClickedIncrement())], ['Increment']),
  ]),
})

Cuatro observaciones que un desarrollador React debería hacer enseguida:

  • El Model es un schema validado, no un useState suelto. Schema.Struct da tipo TypeScript y validación en runtime — el mismo patrón que tu backend Effect usa para sus datos.
  • modifyFields no muta: devuelve un Model nuevo. Nunca verás model.count = 5.
  • Message.match es exhaustivo: si mañana añades ClickedReset a la unión y olvidas el caso en update, TypeScript no compila. Como un reducer, pero sin olvidos posibles.
  • El handler del botón no hace nada: construye el valor Message.ClickedIncrement() y termina. El "hacer" vive en otro sitio.

El giro mental: Messages son hechos, no órdenes

ClickedIncrement no significa "suma uno". Registra que el usuario hizo clic. En este counter, update suma uno. Una versión futura puede pedir el siguiente valor a un servidor. El Message queda igual: es un registro estable del evento.

— foldkit.dev/core/messages

En React el nombre del handler suele ser el nombre de la acción (handleClickIncrement = "incrementa"). Aquí el nombre describe qué pasó y update decide qué significa ahora, con el Model actual en la mano. Las convenciones de nombres lo reflejan: Clicked* (clics), Updated* (inputs), Succeeded*/Failed* (resultados que pueden fallar), Completed* (resultados sin ambigüedad), Got* (hechos de un Submodel hijo).

Commands: efectos como datos

La pregunta obvia: si update es pura y los handlers no hacen nada, ¿dónde vive el fetch? Respuesta: en el segundo valor de retorno de update. Un Command es la descripción de un efecto one-shot; el runtime lo ejecuta y devuelve el resultado como uno de sus Messages declarados (doc: Commands):

// El Command: nombre + Messages posibles + el Effect que produce uno
const DelayReset = Command.define('DelayReset', {
  args: { seconds: Schema.Number },
  messages: [Message.CompletedDelayReset],
  execute: ({ seconds }) =>
    Effect.as(Effect.sleep(`${seconds} seconds`), Message.CompletedDelayReset()),
})

// update: fija el flag Y describe el trabajo pendiente. Nada se ejecuta aquí.
const update = (model: Model, message: Message) =>
  Message.match<Update.Return<Model, Message>>(message, {
    ClickedResetAfterDelay: () => ({
      model: modifyFields(model, { isResetting: () => true }),
      commands: [DelayReset({ seconds: model.resetDuration })],
    }),
    CompletedDelayReset: () => ({
      model: modifyFields(model, { count: () => 0, isResetting: () => false }),
    }),
  })

Fíjate en la secuencia: al hacer clic, el estado cambia inmediatamente (isResetting: true) y la vista ya puede mostrar "Resetting…". El Command DelayReset es un dato que viaja al runtime; cuando el Effect.sleep completa, el runtime despacha CompletedDelayReset y el ciclo vuelve a empezar. Nada ocurre mientras update corre — no hay requests lanzadas a medias, ni timers colgando de un closure.

Para un fetch a tu backend el patrón es idéntico, con dos Messages de resultado: SucceededFetchCount({ count }) y FailedFetchCount({ error }). El fallo no es una excepción que revienta: es un hecho más que llega a update y se convierte en estado explícito del Model (una pantalla de error, un retry). El Command HTTP completo está en la doc de Commands, y será la Lección 0002.

Dónde entra Effect

No necesitas "saber Effect" para esta lección, solo tres datos (foldkit.dev):

  • Un Effect es un valor que describe un cómputo con efectos sin ejecutarlo. Command.execute es un Effect.
  • Schema define datos con validación runtime + tipo derivado. El Model completo y los payloads de Messages son Schemas.
  • El runtime de Effect es quien ejecuta todo eso — con servicios, interrupción y concurrencia incluidas. Toda app Foldkit es un Effect.

Comprueba lo que aprendiste

Cinco preguntas, una sola oportunidad por pregunta — recuperar de memoria es lo que hace que esto se quede grabado.

Ejercicio: traza el flujo

En papel (o en un comentario), sin mirar el código de arriba más de una vez: el Model es { count: 5, isResetting: false, resetDuration: 2 } y el usuario hace clic en "Reset after delay". Escribe los 4 pasos: qué Message se crea, qué devuelve update la primera vez, qué pasa durante los 2 segundos, y qué Message llega después con qué efecto sobre el Model.

Mostrar la solución (intenta primero)
  1. La vista construye ClickedResetAfterDelay(). El runtime lo despacha a update.
  2. update recibe el Model actual y devuelve: Model con isResetting: true (el count sigue en 5) + el Command DelayReset({ seconds: 2 }) como dato. La vista ya renderiza el estado "resetting".
  3. Durante los 2 segundos el runtime ejecuta el Effect (Effect.sleep). update no participa: no espera nada.
  4. A los 2 segundos el runtime despacha CompletedDelayReset(); update produce el Model final: count: 0, isResetting: false.

Si en tu traza update "esperó" o el fetch se "lanzó" dentro del handler: relee la sección Commands. Es el error nº1 de quien viene de React.
